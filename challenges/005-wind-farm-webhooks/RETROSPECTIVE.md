# Challenge 005 Retrospective — Wind Farm Telemetry Webhooks

## Challenge context
- **ID / title:** 005 — Wind Farm Telemetry Webhooks
- **Type / difficulty:** Webhook integration / Level 4
- **Industry / business problem:** Accept authenticated turbine telemetry while preventing forged, duplicate, unknown-turbine, and stale readings from corrupting the status view.
- **Technology stack:** TypeScript, Node.js, Express 5, `node:test`, dotenv, Node crypto.
- **Skills practiced:** HMAC verification over raw request bytes, Express body parsing, runtime payload checks, idempotency, freshness checks, HTTP response behavior, and API verification.
- **Initial familiarity:** Experienced with webhooks and had built an HMAC webhook before, but needed to refresh how signature computation, raw buffers, and manual payload validation worked.
- **Completion status:** Complete.

## Initial understanding and approach
- **My interpretation and desired outcome:** Build a POST webhook route that authenticates provider calls, validates the payload and turbine, acknowledges duplicate deliveries, rejects stale readings, and updates the turbine for a new valid event.
- **Requirements, constraints, and verified facts:** The provider signs the exact raw body with HMAC-SHA256 and sends a hex digest in `x-telemetry-signature`. Event IDs identify deliveries; `reportedAt` determines freshness; state may remain process-local for this challenge.
- **Initial plan and alternatives considered:** Use an early-return route layout. I expected the HMAC work to be familiar and the route to be straightforward. I did not initially remember the raw-body handling details or how to validate the payload shape without a library such as Zod.
- **Assumptions:** I initially thought the signature might be decrypted with the secret. That was corrected: HMAC is recomputed and compared, not decrypted.

## Implementation journey
- **Major steps and decisions:** Built the route around signature checks, payload validation, turbine lookup, duplicate detection, stale-reading detection, event storage, and turbine mutation. Added an event store and webhook payload type after noticing those were missing from my initial outline.
- **Unexpected behavior / obstacles:** `express.json()` puts a parsed object in `req.body`; passing that object to `Hmac.update()` caused a type/runtime error. The signature must use the exact raw request bytes, so the raw buffer is retained through the JSON parser's `verify` callback. TypeScript also typed that callback's request as `IncomingMessage`, requiring a local request type assertion to attach/access `rawBody`.
- **Mistakes or incorrect assumptions and corrections:** I initially thought HMAC involved decryption. I also initially compared a stored reading timestamp against the turbine ID in the stale check; tracing the expression made the mismatch clear, and the check was changed to compare timestamps. A later test showed that freshness must also be compared against the turbine's seeded/current reading, not only previously stored webhook events.
- **How the approach changed / where I got stuck and progressed:** The route structure itself was easy. Most of the roughly two hours (my estimate) went into refreshing HMAC/raw-buffer handling and runtime payload validation. I identified and implemented the initially missed event store and event payload shape.

## Technical implementation
- **Changes and how they work:** `src/app.ts` preserves the raw body via `express.json({ verify })`, computes the expected digest with `createHmac`, validates the signature format and compares digest buffers with `timingSafeEqual`, validates the parsed body shape, finds the turbine, acknowledges duplicate event IDs, rejects readings older than the turbine's current `reportedAt`, and otherwise records the event and updates turbine fields.
- **Data and control flow:** Raw bytes are used for signature verification; parsed `req.body` is used only after authentication for shape checks and business logic. The event store tracks accepted event IDs in process memory.
- **Architecture, configuration, integration details:** `HMAC_SECRET` is loaded from the ignored local `.env.local` through dotenv. The API remains process-local as required by the challenge.
- **Trade-offs and limitations:** The process-local event and turbine stores reset on restart and are not shared across instances. The payload shape check establishes types, not domain plausibility; acceptable numeric ranges require an explicit business rule.
- **Relevant files, functions, tests, and commands:** `src/app.ts` (`verifySignature`, `isWebhook`, `updateInfo`, `POST /webhooks/telemetry`); `test/webhook-responses.test.ts`; `test/app.test.ts`; `README.md`; `npm test`; `npm run typecheck`.

## Lessons learned
- **New concepts / clarified knowledge / corrected misconceptions:** HMAC signatures are computed over bytes and compared; they are not encrypted. Parsed JSON is not a substitute for the original serialized request body. A matching HMAC confirms possession of the shared secret and integrity of the signed bytes, not the semantic truth of payload values. Structural runtime checks do not replace domain validation.
- **Skills to strengthen; what I would do differently:** Revisit HMAC/Buffer APIs and plan raw-body handling before adding JSON parsing. Define payload validity and response behavior explicitly. Be careful to compare timestamps with timestamps and to consider the current seeded state as well as previously accepted events.
- **Application to real-world engineering:** A process-local event ledger is sufficient for this exercise but is not durable or shared. Production idempotency needs persistent shared state and coordination with the state update.

## Production considerations
- **Changes needed for production:** Persist event IDs and turbine state in shared durable storage; enforce event-ID uniqueness and make recording the event plus updating turbine state atomic. Define domain-valid status, timestamp, and measurement ranges.
- **Relevant security, scalability, reliability, monitoring, and maintenance:** Keep the signing secret in a secrets manager, rotate it safely, preserve raw request bytes for verification, use timing-safe digest comparison after signature-format/length validation, and monitor rejected signatures, invalid payloads, duplicates, stale readings, and processing failures. A backup helps recovery but does not itself prevent a live replay from being accepted.
- **Additional tests or validation needed:** Persistence/restart and multi-instance idempotency tests; business-rule boundary tests once valid ranges are defined; malformed JSON and content-encoding behavior; provider-specific contract verification.
